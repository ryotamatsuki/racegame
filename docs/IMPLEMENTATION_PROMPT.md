# 生成AIへの実装プロンプト

以下の本文を、GitHubの読書きとブラウザ検証が可能な生成AIに渡してください。
このプロンプトはゲーム実装を始めるためのものであり、仕様書作成時点ではゲームは未実装です。

## コピーして使う本文

あなたは、Three.js、TypeScript、ブラウザゲーム、車両シミュレーション、3Dモデル制作、スマホ最適化、GitHub Actions、GitHub Pagesに対応する実装担当者です。
以下のリポジトリを実際に読み、仕様に従うゲームを実装し、検証し、GitHub Pagesで遊べる状態まで仕上げてください。

仕様書：

実装プロンプト：

### 依頼の目的

ミニ四駆の機種を選び、パーツをセッティングし、改造したマシンでCPUと競える3Dブラウザゲームを作成してください。
説明、設計案、擬似コード、デモ画面だけで終わらず、実際に遊べる成果物をリポジトリに保存してください。
コードのコミット、通常のpush、必要なPages設定と公開まで実行してください。
既存のブランチ保護と承認ルールがある場合は遵守し、回避しないでください。
ユーザーの明示的な許可なくforce push、既存成果物の大量削除、別サービスへの公開先変更をしないでください。
サブエージェントは使わず、単独で進めてください。

### 最初に行うこと

1. 対象リポジトリの既定ブランチ、最新コミット、作業ツリー、README、AGENTS.mdがあればその内容を確認してください。
2. docs/GAME_SPEC.mdと本ファイルを全文読んでください。
3. 既存実装やIMPLEMENTATION_STATUS.mdがあれば確認し、完了済みの作業を作り直さず不足分から進めてください。
4. 必須要件F01〜F11と受入条件A01〜A16を作業計画に対応付けてください。
5. リポジトリを取得できない場合は、読んだふりをせず、阻害要因を明示してください。

仕様とこのプロンプトが競合した場合、ゲームの詳細はGAME_SPEC.mdを優先してください。
以後にユーザーが明示した変更は反映し、文書も更新してください。
合理的に決められる細部は自分で決め、理由を記録して続行してください。
仕様の必須要件を削る必要が生じた場合だけ、その影響を明示してください。

### 求める見た目

参考URLは https://storm-race.vercel.app/ です。
このサイトにアクセスできなくても作業を止めないでください。
参考サイトは内部実装を確認済みではなく、素材やソースのコピー元でもありません。

次の視覚的な特徴を独自の素材で表現してください。

- 木の作業机、緑系のカッティングマット、工具、部品トレーを備えた工房。
- 中央に大きく置いた、塗装、キャノピー、翼、車輪、ローラーが識別できる精細なマシン。
- 下部に部品カテゴリと候補、側面に性能比較がある、操作しやすいガレージ。
- 部品ごとに離れる分解表示、部品の拡大、回転、再組立。
- 高架、バンク、立体交差、ジャンプ、垂直ループを備えた模型コース。
- 車体を近くから追うカメラ、車載、沿道、全景、映画的な自動切替。
- 控えめな反射、接地影、材質の違いで模型らしい質感を作る。

単純な箱型の車体や色替えだけの機種差を完成版にしないでください。
3Dモデルは独自の手続き的メッシュでもGLBでもよいですが、部品単位で交換と分解ができるようにしてください。
外部の有料サービスやユーザーによる素材準備がなくても完成できる方法を選んでください。
実在の作品名、マシン名、ロゴをそのまま使わず、仕様書の仮名称等から独自に作成してください。

### 技術構成

Three.js + TypeScript + Vite + Reactを基本としてください。
Three.jsに描画、Reactにガレージ等のUI、独立したTypeScriptモジュールに走行計算を担当させてください。
ライブラリは実装時の公式資料で互換性を確認し、実際に動く版とlockfileを保存してください。
毎フレームReact全体を更新しないでください。
SSR、バックエンド、データベース、APIキーを実行要件にしないでください。

シミュレーションはDOMやWebGLなしでテスト可能にしてください。
部品定義、装着状態、導出性能、レース状態、描画オブジェクトを分離してください。
コース形状と車体の走行経路を同じデータから生成してください。
状態やイベントリスナー、GPU資源、音源の所有者を明確にしてください。

### ゲームの必須機能

- シルエットが異なる4機種。
- ボディー、シャーシ、モーター、ギヤ、タイヤ、ローラー、電池、ウイング、ブレーキの9カテゴリに各3種類以上。
- パーツ交換を3D表示と走行性能の両方へ反映。
- 互換性判定、変更前後比較、説明、標準構成への復元。
- 構成3枠以上と設定、自己ベストの端末内保存。
- ガレージの回転、ズーム、分解、組立、部品拡大、車輪回転。
- 自車とCPU3台、3周のレースとタイムアタック。
- 入門、テクニカル、ループの3コース。
- カウントダウン、順位、周回、時間、速度、コース図。
- 追尾、車載、コース脇、全景、自動演出の5視点。
- 一時停止、復帰、完走、DNF、結果、再挑戦、改造へ戻る流れ。
- 日本語UI、PCキーボードとタッチの両対応。
- 効果音、回転数に連動するモーター音、音量とミュート。
- 画質設定、WebGL非対応やコンテキスト喪失時の明示的な案内。

初回は自動走行を基本とし、ブースト、姿勢操作、天候、オンライン対戦を先に追加しないでください。
必須機能と受入試験の達成を優先してください。

### 走行計算で守ること

固定時間刻みと描画補間を使い、画面のFPSで車の速度や結果が変わらないようにしてください。
通常走行は弧長で管理し、勾配、曲率、バンク、路面法線を使って位置と姿勢を決めてください。
ループや閉路の継ぎ目で姿勢が反転しないようにしてください。

モーターのトルク曲線、減速比、タイヤ半径、質量、重力、抵抗、ブレーキを結びつけてください。
ゲーム用の近似式と調整値は説明を残し、実測値と偽らないでください。
速度不足のループ通過、ジャンプ面のすり抜け、高架と下の路面の取り違えを防いでください。
事故を単なるランダム抽選だけで決めないでください。

CPUにも同じモデルを使ってください。
順位をあらかじめ決めたり、自車だけに隠れた補正をかけたりしないでください。
固定レーンの長さの差を考慮し、周回と共通チェックポイントから順位を計算してください。
同じレーンとseedの比較走行で、パーツのトレードオフを検証してください。
全コースで同じ構成が常に最良となる単純な加点方式を避けてください。

### 実装の進め方

段階1では、起動からガレージ、1台の走行、結果までつながる最小の一周を作ってください。
段階2では、4機種、全パーツ、分解、比較、保存を完成してください。
段階3では、CPU、3コース、ループとジャンプ、順位とDNFを完成してください。
段階4では、5カメラ、音、スマホ操作、素材と照明、結果助言を仕上げてください。
段階5では、性能測定、受入試験、修正、Pages公開、公開URLの実操作を行ってください。

各段階は中間成果であり、そのたびに許可を求めて終了しないでください。
単独で作業を継続し、機能単位でコミットしてください。
docs/IMPLEMENTATION_STATUS.mdに、完了、未完了、次に行う具体的な作業を記録してください。
作業を中断せざるを得ない場合も、次の担当が再開できる状態を残してください。

### 検証と公開

型検査、走行モデルテスト、本番ビルド、実ブラウザE2Eを実施してください。
テストは仕様書A01〜A16に対応付けてください。
スタート画面やDOMだけでPASSとせず、3Dの車体とコースが描かれ、走り、結果に到達することを確認してください。
3コースの完走、全機種選択、各カテゴリ交換、保存復元、5視点、停止復帰、スマホ操作を確認してください。
画像または短い動画を証拠として残し、見えていないものを見えたと書かないでください。

実ブラウザでWebGLが動かない場合は、その描画試験をBLOCKEDとして記録してください。
ビルド成功やActions成功で代用しないでください。
実スマホを使用できない場合は、画面サイズのエミュレーションと実機確認を区別してください。
性能は測定端末、ブラウザ、画質、解像度、中央値とp95フレーム時間を記録してください。

GitHub Pagesの公開先は /racegame/ です。
Viteのbaseと全素材のURLを対応させ、サブパスでの再読込も確認してください。
mainへのpushとworkflow_dispatchでビルドしてdistをPagesへ配信するActionsを作成してください。
PRの検証と公開は分離してください。
必要な設定権限がある場合はPages SourceをGitHub Actionsに設定し、デプロイ完了まで確認してください。
権限不足の場合は設定手順を具体的に残し、公開済みと書かないでください。

公開後に予定URLを開き、ガレージからレース結果まで実際に操作してください。
コード保存、デプロイ成功、公開サイトの操作確認を別々の事実として報告してください。
